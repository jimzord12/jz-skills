# Contributing & Repo Conventions

How this skill library is structured, versioned, and distributed. This is the operational
companion to `CONTEXT.md` (which holds the domain glossary and workflow vision).

---

## The three-location law

Skills live in three places, each with a distinct, non-overlapping role. Treat this as a law,
not a vibe:

| Location | Role | Editable? | Git-tracked? |
| --- | --- | --- | --- |
| `.agents/skills/<name>/` | **Base skills** — vendored from upstream via `npx skills add`, pinned in `skills-lock.json`. | **No — read-only.** Managed only by the `skills` CLI. | Yes |
| `skills/<domain>/<sub>/<name>/` | **Your own skills** — new skills and forks. **The source of truth for everything you own.** | **Yes.** Edit freely. | Yes |
| `.claude/skills/<name>` | **Discovery view** — a generated set of symlinks so Claude Code can find every skill. | **No — disposable.** Regenerated by a script. | No (gitignored) |

### Read-only base, fork before edit

`.agents/skills/` is managed entirely by `npx skills add` + `skills-lock.json`. **Never hand-edit a
base skill** — your changes will be silently clobbered the next time that skill is re-pulled.

Want to change a base skill? **Fork it first:**

1. Copy the skill into `skills/<domain>/<sub>/<name>/`.
2. Give the fork a **distinct name** (e.g. `to-prd` → `to-prd-seams`, `handoff` → `handoff-local`).
3. Add the `metadata.original_skill` block (see [Versioning](#versioning)) so the provenance is recorded.
4. Edit the fork. Leave the base untouched.

### The discovery view is generated — never edit `.claude/skills/`

`.claude/skills/` is **not** source. It is a set of symlinks regenerated by
`scripts/sync-skills.mjs` and is gitignored (committed symlinks break on Windows). Editing a file
*through* a symlink there writes the real source file — fine — but never create, delete, or commit
anything in `.claude/skills/` directly.

## Syncing discovery

After any of these — `npx skills add`, creating a new own skill, adding a fork, deleting a skill —
regenerate the discovery view:

```sh
node scripts/sync-skills.mjs
```

What it does:

- Finds every directory containing a `SKILL.md` under `.agents/skills/` and `skills/`.
- Skips `skills/deprecated/**` and `skills/in-progress/**` (not exposed in discovery).
- Identifies each skill by its frontmatter `name:`.
- On a name collision between a base skill and an own skill, **the own fork wins** (logged as an
  override). Same-name entries resolving to the same real path are de-duplicated.
- Two own skills sharing a name is a hard error.
- Wipes and recreates `.claude/skills/` as relative symlinks, then prints a summary.

## Versioning

Two layers, kept in sync:

1. **Repo-level — annotated git tags `vX.Y.Z`.** This is the unit that `skills` CLI consumers
   actually pin (via commit/tag in their own `skills-lock.json`).
2. **Per-skill — `metadata.version` semver** in each own skill's frontmatter, bumped whenever that
   skill's `SKILL.md` or bundled files change. Base skills are exempt.

Frontmatter schema for an **own** skill:

```yaml
metadata:
  version: 0.1.0          # semver — bump when THIS skill changes
  author: jimzord12
  created_at: Jun 17, 2026
  updated_at: Jun 17, 2026
```

For a **fork**, also record provenance:

```yaml
metadata:
  original_skill:
    {
      name: to-prd,
      author: Matt Pocock,
      local_path: .agents/skills/to-prd,
      repo_url: https://github.com/mattpocock/skills/tree/main/skills/engineering/to-prd,
    }
  version: 1.0.0
  created_at: Jun 17, 2026
  updated_at: Jun 17, 2026
```

Enforce it before tagging a release:

```sh
node scripts/check-skill-versions.mjs
```

It is changesets-style: for every own skill, if anything in the skill's directory changed since the
last `v*` tag but `metadata.version` wasn't bumped, it fails and lists the offenders. With no
release tag yet, it passes (nothing to diff against).

## Distribution

There is **no publish step.** The `skills` CLI uses GitHub as the registry.

- Install an own skill by path:

  ```sh
  npx skills add jimzord12/jz-skills/skills/productivity/cnp
  ```

- "Release" by tagging:

  ```sh
  git tag -a v0.3.0 -m "…" && git push --tags
  ```

  Consumers pin to a tag/commit for reproducibility via their own `skills-lock.json`.

## What's tracked under `.claude/`

- **Tracked (shareable):** `.claude/agents/`, `.claude/hooks/`, `.claude/settings.json`.
- **Ignored:** `.claude/skills/` (generated) and `.claude/settings.local.json` (per-machine).
